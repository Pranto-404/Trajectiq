Feature engineers add requests here instead of editing shared files (src/store, src/ds, src/shell, package.json). Each entry: who asks, what, why, and the workaround in place.

## From WP7/WP8 (flight, crew), branch feat-flight-crew

1. **Store: consume the forecast in `ask`** (WP1, `src/store/createGame.js` `askAssistant`). The copilot answer for "Use my one forecast" carries `consumesForecast: true` but nothing increments `run.forecasts`, so "one forecast per mission" is not enforced (the v6 app had the same gap). Please do `set(s => ({run: {...s.run, forecasts: (s.run.forecasts || 0) + 1}}))` when `answer.consumesForecast` and a crisis is pending. Workaround: `spendForecast()` in `src/features/flight/IncidentTakeover.jsx` bumps `run.forecasts` through `useGame.setState` after `ask` resolves (the checkpoint writer persists it). Remove the workaround when the store does it; the test `the one forecast per mission` keeps passing either way as long as the count ends at 1.
2. **Store: `crew-signoff` re-opens `launch-check`** (WP1). `crew-signoff` always calls `gameReview()`, which replaces whatever sheet is open with `launch-check`. The standalone `rollcall` sheet (WP8) therefore turns into the built-in launch check after the first sign-off. Fine when the hangar embeds `<RollCall/>` in its own `launch-check` sheet; if you want the standalone sheet to stay open, make `gameReview()` skip `openSheet` when `sheet.id === 'rollcall'`.
3. **Hangar (WP5): use the crew components.** Replace the Go / No-Go block of the built-in `launch-check` with `import {RollCall, CrewStrip} from '@/features/crew/index.js'`: `<RollCall/>` reads the store itself (verdicts, sign-offs, solo or crew) and plays the sequential console animation; `<CrewStrip/>` is the crew table with pass-the-controls and proposals.
4. **Shell: `Stage3D` contract.** Flight loads `Stage3D` through `import.meta.glob('../stage/index.js')` (named export `Stage3D`), so it works before and after the stage package lands. If the stage exports it under another name or only as a default screen, tell WP8/WP7 or export `Stage3D` from `src/features/stage/index.js`. Props passed: `design, selected=null, hoverPart=null, run (read-only past view when scrubbing), phase, quality="auto", reduced, onPick, onSocketHover`. Until then the SVG `FlightSchematic` is shown.
5. **DS: gauge `compact` density.** `Gauge` has no compact form, so flight trims it with CSS (`max-width` on the arc dial, pair layout, hidden thresholds on short screens). A `size="sm"` prop (arc 100 px, linear without the foot row) would remove the overrides.
6. **Build hygiene:** `npm test` regenerates the committed legacy `dist/TRAJECTIQ_Play.html` (the legacy standalone builder runs inside a node test). It shows up as a modified file after every run; feature branches should not commit it. Consider making the test write to a temp file.

# Feature requests for shared files

Written by feature packages that must not edit shared files (`src/store`, `src/ds`, `src/shell`, `package.json`). Each entry names the owner, what is needed and the workaround in use.

## From WP4 board / WP5 hangar (`feat-board-hangar`)

1. **Store `setDestination` accepts only `moon` and `mars`** (`src/store/createGame.js`, the `['moon', 'mars'].includes(destination)` guard). The engine now has 8 bodies. Workaround: the hangar destination select calls `board-scenario` with the body's default scenario (`DEFAULT_SCENARIO[body]`, else its first scenario), which already loads that body's starter design. Wanted: let `setDestination` take any `isBodyId`, and make it call `presetFor(destination, 'balanced', defaultScenario)`.
2. **Store `preset(name)` drops scenario, difficulty, sandbox and livery** (`normalize(presetFor(s.design.destination, name))`). v6 behaved the same, but with 10 scenarios it silently resets "Lunar Ice Hunter / Cadet" to the default scenario. Workaround: Quick launch re-applies scenario, difficulty and sandbox through `board-scenario`, `board-difficulty`, `board-mode` after the preset. Wanted: `preset` keeps `scenario`, `difficulty`, `sandbox`, `livery`, `name`, and uses `presetFor(destination, key, scenario)` so the preset fits the scenario (array scale, altitude).
3. **Shell layout: the single grid column grows to the widest line of text at 375 px** (`.shell` has `grid-template-rows` only, and the header has `nowrap` items). At 375 px `document.scrollWidth` is about 495. Wanted: `.shell { grid-template-columns: minmax(0, 1fr); }` and a header that scrolls or wraps (`.nav` already scrolls; the right-hand group does not). Workaround: `.screen` in board and hangar is capped at `100vw - 2 * gap`, so page content fits, but the header still overflows horizontally.
4. **`prefs.guided` / `guide` index**: there is no action to reset the onboarding step (`guide-next` only goes up, `guide-toggle` flips the preference). The spotlight keeps its step in component state, so turning guided help back on restarts at step one. Wanted: `guide-reset` (or `guide-toggle` setting `guide: 0` when it turns on).
5. **Shell `Screen` transition is `mode="wait"`**, so two screens are never mounted together and a `layoutId` shared element cannot connect the scenario card to the hangar title. Workaround: FLIP hand-off through `src/features/board/flip.js` (measured rectangle). Nothing needed unless the shell moves to overlapping transitions.
6. **Roll call hook-up**: the launch-check sheet (id `launch-check`, owned here) lists role sign-offs itself and shows an "Open the roll call" button only when a `rollcall` sheet is registered (`hasSheet('rollcall')`). The crew package should either register `rollcall` (button then appears) or export a component the launch sheet can embed; tell WP4/5 which.
7. **Stage contract**: the hangar picks up `Stage3D` from `src/features/stage/index.js` if that entry exports it (`Stage3D` or `default.Stage3D`), with props `design selected hoverPart run phase quality reduced onPick onSocketHover fallback` and an imperative ref `{seatPart(kind, id, fromRect), cameraTo(preset), launchSequence(skip)}`. Without it the built-in SVG schematic stage is used. `Stage3D` should be exported lazily (`React.lazy`) so the stage chunk stays out of the initial JS budget (the budget test is at 220 KB gzip and the main chunk is already near it).
